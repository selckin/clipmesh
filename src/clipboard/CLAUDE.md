# src/clipboard

Clipboard backends. Supplements `../CLAUDE.md` (engine-side module notes) and `../../CLAUDE.md` (overview, cross-cutting invariants — notably "Startup content comes from the backend").

- **`clipboard/`** — the `Clipboard` trait (`watch`/`list_types`/`read_offer`/`write_offer`). `list_types` and `read_offer`'s `only` argument exist because a content read is *not* cheap here — the Wayland backend spends a connection and a roundtrip **per representation** — so a caller that wants one type, or only the names, must be able to say so before the reads happen. `wayland.rs` is the real in-process backend; `watch.rs` is its change listener (runs on a dedicated thread because Wayland dispatch blocks); `mock.rs` backs every test (`block_reads`/`allow_reads` gate reads, which is what makes the `Initial`-contract tests exact rather than hopeful; `drop_all_representations` models the backend's own over-budget skip, the case that made an oversized clipboard look empty). **`watch.rs` distinguishes `Connect::{Subscribe, Reconnect}`**: only the first connection is the `watch` call, so only it reports `Initial`. The watcher is supervised, and reporting a reconnect's startup burst as `Initial` fed `adopt_restored` — which records at stamp 0 and never broadcasts — with content the user had copied while the compositor was away, where any peer's older clipboard outranked it. A reconnect reports `Changed` instead, which also means it reads no content at all. The subscribe's read is bounded by `read_offer_bounded` (a detached thread + `recv_timeout`), because it runs ahead of the dispatch loop that detects every clipboard change on this host: unbounded, one unresponsive selection owner left the daemon permanently deaf with `watch_once` never returning for `supervise` to restart. `io.rs` is `ClipboardIo`, the engine's sole gateway (see the echo-suppression bullet under `sync.rs` in `src/CLAUDE.md`). `atoms.rs` owns X11/ICCCM selection-atom semantics — which atoms carry content, which are pure machinery, and what encoding each declares — because that is neither an engine policy nor a Wayland detail; `wayland.rs` and `sync.rs` both consume it instead of each keeping its own overlapping-but-different list. `budget.rs` is `OfferBudget`, the per-representation policy (dedup, machinery, greedy advertise-order byte budget) both backends assemble their offers on — the Wayland loop is blocking and the Mutter loop is async, so the decision lives in neither. **`mutter.rs` is the GNOME backend** (spec: `docs/superpowers/specs/2026-09-02-mutter-clipboard-backend-design.md`): one tokio task holds a `org.gnome.Mutter.RemoteDesktop.Session` with the clipboard enabled (never `Start`ed — that is what raises GNOME's "remote desktop" indicator), supervised by `backoff::supervise_async`, and shares its state with the trait methods. Three of Mutter's rules shape it: our own content cannot be read back through Mutter, so while the session is owner reads come from the offer we set (also the echo path); one `SelectionRead` may be pending per session, so reads take a lock (the engine and the `--paste` server overlap); and Mutter announces the current owner from inside `EnableClipboard`, before the reply, so the `Initial` drain (`now_or_never` on a stream created before the call) is exact rather than timed. `SelectionOwnerChanged` is also the only source of the type list, so `list_types` costs nothing there. CLIPBOARD only: `Backend::select` refuses `sync_selection`/`link_selections` on this backend up front, and the Selection arms of the trait methods are defence in depth. Two further rules the review found the hard way: a **failed `SetSelection` restores the previous `owned` offer** (clearing it leaves `is_owner` true with nothing readable or servable — a clipboard dead until the next copy), and the **subscriber list and "is a task running" flag sit under one lock**, with every task exit going through `attempt_finished`, so a task retiring down an error path cannot strand a later `watch`. `backend = "auto"` treats a *failed* Wayland probe as "no data-control" rather than fatal, because the Mutter backend needs only D-Bus and a GNOME host whose `WAYLAND_DISPLAY` never reached the service environment would otherwise restart-loop. Mutter's clipboard manager fetches text/image right after every owner change and takes over with one saved type when the source app exits — the latter arrives as a `Changed` and re-broadcasts a narrowed offer once (documented in the README, not worked around).
